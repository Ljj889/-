# R-009 模块可移除性红线：可删除性优先于整洁性

**当** 立下"删掉某模块目录仍能编译运行"这类解耦目标 → **易犯** 为求整洁把**宿主相关代码也收进子模块**（典型：建表 SQL、宿主配置、共享常量），结果宿主文件反过来 `import` 它 —— 删目录即编译断裂，**目标与做法自相矛盾**（本次实测：若把 `STICKY_SCHEMA_SQL` 放进 `sticky/sticky-schema.ts` 再由 `database.ts` 引用，删目录后 `database.ts` 直接挂）→ **护栏**：

1. **判定原则：可移除性 > 整洁性。** 子模块目录只放"自身逻辑"；与宿主强耦合的代码**内联在宿主文件**，沿用宿主既有惯例（本次：建表 SQL 与 `PET_SCHEMA_SQL` / `AI_SCHEMA_SQL` 并列内联于 `database.ts`）。这样删目录后宿主最多残留一个无人引用的常量，照常编译。
2. **反向依赖用回调注入替代直接 import**：宿主（如托盘菜单、主窗工具栏）需要调用子模块能力时，由**装配文件传回调**，而不是让宿主 `import` 子模块。本次实测：`TrayManager(windows, { onResetSticky })` —— 托盘文件对便签模块零 import，且能力未注入时菜单项自动隐藏。
3. **验收法（可脚本化）**：`grep <子模块名>` 全仓，外部引用必须**收敛到单一装配文件**；把该文件里的命中行数列为"删除时的清理清单"。本次结果：全仓仅 `src/main/index.ts` 引用 sticky 模块（5 行）→ 删目录只需清 4 处。

**为什么值得立为红线**：AI / 人在多轮后会自然遗忘这类跨文件约束（rule 64 物理规律），而它**可 grep 硬校验**——不做成红线，解耦目标通常会在第 3 个 Wave 悄悄失守，且失守时无人察觉。

**关联**：rule 64（硬约束优先，能脚本化的一律引擎化）、rule 18（接口契约层）、rule 49（调度器机械豁免的边界，>10 行改动仍须路由子 Agent）、L2（依赖方向：子模块不得反向依赖宿主）。
