# 对抗式双架构师设计回路 Playbook（rule 74）

> 将"多架构师并行独立拆解"从 rule 20 的可选「重量档」升级为**非平凡设计/讨论阶段（Phase -1.5）的默认机制**，并显式引入挑刺 Agent（Red Team）+ 上网调研工具（rule 75），治"单架构师空降易走偏 / 不全面"。
> 外部实证：Du et al. 2023（arXiv:2305.14325）multi-agent debate 实证多实例提案 + 多轮互批显著提升推理/事实准确率、多数收敛到更准确共识；Anthropic/Google ADK 强调子 Agent 独立上下文隔离（"用通信共享记忆，不用共享内存"）。

---

## 1. 目的与定位

- **升级点**：单架构师"空降"视角单一、易走偏。改为**架构师 A / B 互不可见独立提案 → 交叉互审 → 挑刺 Agent 批 → 收敛共识**，把"靠自觉全面"变成"结构化对抗 + 硬收敛"。
- **不是新框架**：是 rule 20 重量档的正式化 + 默认化 + 挑刺 Agent 显式化，落在 Phase -1.5（人机设计锁定）的讨论/设计环节。

### 适用（启用）
- 架构选型 / 技术决策两难
- 模块拆解有争议、多方案难取舍
- 设计讨论阶段（Phase -1.5）的非平凡设计

### 不适用（走 rule 20 轻量档单架构师 + 架构评审）
- 小设计、小改动、纯执行任务（rule 46 编排出口 / Anthropic 反过度分工护栏）

---

## 2. 角色

| 角色 | 层 | 职责 | 边界 |
|---|---|---|---|
| 架构师 A | L1 平级 | 独立读目标 → 写 `proposal_A.md` | **不可见 B 的提案** |
| 架构师 B | L1 平级 | 独立读目标 → 写 `proposal_B.md` | **不可见 A 的提案** |
| 挑刺 Agent（Red Team） | L1 平级（与知识沉淀同级） | 吃 A+B+互审 → 产出 `critique.md` | 只挑刺、不写方案 |
| L0 调度器 | L0 | 路由、派发、组织回合、判共识门槛、升级人 | **只路由不创作**（rule 12） |

> "互不可见"是关键：避免锚定偏差——若 B 先看到 A，B 只是 A 的附议，对抗失效。L0 给 A、B 各自**完整但独立**的上下文（目标 + 调研素材），不共享彼此的输出。

---

## 3. 回合协议

```
Round 1
  1. A、B 各自独立读目标 + 上网调研（配 rule 75 crawler），互不共享上下文
     → 各写 proposal_A.md / proposal_B.md
  2. 交叉互审：A 审 B 写 review_A_on_B.md，B 审 A 写 review_B_on_A.md
     （逐条 diff：同意 / 分歧+理由+建议融合）
  3. 挑刺 Agent 吃四份文档 → critique.md（P0 必改 / P1 建议 / 视角扩展）

Round 2
  4. A、B 各吸收合理点（互审 + 挑刺）修订 proposal

收敛判定（L0）
  5. 对比差异：
     - 差异收敛到仅次要项（无 P0/P1 核心架构分歧）→ 融合 consensus.md
       → 进入拆模块 / 契约(interfaces.md) / 开发
     - 仍有重大分歧 → Round 3
  6. 熔断：最多 3 轮仍重大分歧 → 升级给人（家俊）裁决（rule 35 人在回路）
```

**共识门槛**：无 P0/P1 级核心架构分歧，仅命名/次要实现细节可议。
**熔断上限**：3 轮（与 rule 34 / rule 57 硬迭代上限同源；概率系统不能当确定性流水线）。

## 4. 模板

### 4.1 proposal_X.md（架构师 A / B 各一份）
```
# 提案 X（架构师 _）
## 1. 目标理解
  我读到的真实需求 / 约束 / 隐含假设
## 2. 架构选型
  主方案 + 备选 + 取舍理由（含 rule 75 调研支撑）
## 3. 模块拆解
  清单 + 职责 + 依赖 DAG（谁依赖谁 ↔ 谁消费谁）
## 4. 接口契约草案
  关键签名 / 数据流 / 事件（对齐 interfaces.md 字段约定）
## 5. 风险与假设
  哪些是我猜的 → 标 [假设]
## 6. 调研引用
  rule 75 上网结论，逐条标 [事实]/[假设]（rule 5 分级）
```

### 4.2 review_X_on_Y.md（交叉互审）
```
# 互审：X 审 Y
## 一致点
## 分歧点（逐条）
  Y 原意 | X 异议 | 建议融合 | 优先级 P0|P1
## 遗漏
  Y 没覆盖但重要的
```

### 4.3 critique.md（挑刺 Agent / Red Team）
```
# Red Team 挑刺报告
## P0 必改
  会导致翻车 / 核心遗漏 / 假设不成立（必须解决才能进开发）
## P1 建议
  过度设计 / 可简化 / 视角盲区
## 视角扩展
  X、Y 都没想到但值得讨论的（扩展思考角度，这正是加挑刺 Agent 的目的）
```

### 4.4 consensus.md（融合稿，L0 组织）
```
# 共识设计（融合稿）
## 采纳 A 的：...
## 采纳 B 的：...
## 吸收挑刺的：...
## 待定 / 升级人项：...
## 进入下一步：拆模块 → interfaces.md（rule 18）
```

## 5. 成本与护栏

- **成本纪律**：架构师 = reasoning 档（最贵），双架构师成本 ≈ 2×；每轮显式记录 `cost_log.md`（rule 38/53，含异常类型列 rule 53）。
- **门控（防过度拆分）**：仅非平凡设计启用（rule 46 编排出口 + rule 74 门控）；小设计回轻量档单架构师。Anthropic/Manus 明确警告"组织架构图式"过度分工只增协调成本、不增收益——本回路以门控规避。
- **互不可见 = 避免锚定**；L0 显式派发上下文 = Anthropic/Google ADK 独立上下文隔离原则落地。

---

## 6. 与既有规则衔接

- **rule 20 架构交叉验证**：轻量档（1 架构师 + 评审）仍用于小设计；重量档升级为本回路，非平凡设计默认。
- **rule 46 编排出口**：小任务单 Agent 直做，不进编排；本回路只在需多视角设计时启用。
- **rule 35 人在回路**：3 轮熔断 / 数据不可逆 → 升级给人（家俊）裁决。
- **rule 65 设计锁定**：consensus.md 是 Phase -1.5 设计锁定的输入之一；最终结果仍须经用户逐项确认（design.md + skeleton + decisions_pending）。
- **rule 75 调研配 crawler**：架构师调研工具配置。
- **Phase -2 调研**：本回路的"调研"阶段复用 Phase -2 Swarm 调研 Agent + rule 75 工具。
