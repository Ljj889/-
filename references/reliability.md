# 可靠性工程：反思、失败恢复、上下文管理

多 Agent 系统在生产环境最大的三个杀手：**重试不改进、失败拖垮全局、上下文爆炸烧钱**。本文件给出三层对策。

## 一、Reflexion 反思循环（重试 ≠ 改进）

"再跑一遍"或"调高温度"都是碰运气——模型没有失败记忆，会重复同一个错误。Reflexion（Shinn et al. 2023）把自我改进拆成三角色闭环：

```
Actor（行动者）执行任务 → Evaluator（评估器）判定成功/失败
→ 失败时 Self-Reflection（反思者）写"教训" → 教训回灌下一轮 Actor 的提示词
```

**关键中的关键：反思结果必须回灌到下一轮输入。** 写了教训却没喂回给执行者 = 没写。

在六层框架里的落地：
1. 审查 FAIL 时，审查员不只给 PASS/FAIL，必须产出**具体的修改要求**（"在 timer.start() 里对负数入参 raise ValueError，并在 docstring 注明"）
2. 把上一版代码 + 修改要求**原样拼进**新任务说明（见 task_templates.md 的 LOOP 注入示例）
3. 失败教训追加到 `lessons.md`："尝试 X → 失败(原因) → 换 Y → 成功"，防止同类错误重复踩坑

## 二、失败分类与恢复策略

### 2.1 失败分类（先分类再处理，禁止一律重试）

| 失败类型 | 特征 | 处理 |
|---|---|---|
| 格式/校验错 | JSON 解析失败、字段缺失 | 带具体报错重试（把报错文本回灌提示词） |
| 逻辑错 | 代码跑通但行为不对 | 带审查反馈重试 |
| 架构错 | 拆解方向本身有问题 | 回到规格/拆解阶段重来 |
| 瞬时错 | 网络/超时等基础设施 | 直接重试即可 |

### 2.2 熔断（Circuit Breaker）

同一子 Agent 连续失败 **3 次** → 停止继续重派该 Agent：
- 换实现思路（换个提示词角度）
- 或向用户升级，说明卡点
- 防止"一个 Agent 的失败级联拖垮整个系统"

### 2.3 三层降级

| 层级 | 策略 |
|---|---|
| Agent 级 | 重试失败的单个调用 |
| 模式级 | 路由到替代 Agent |
| 系统级 | 返回部分结果（其余模块先交付，失败模块标注说明） |

**单个 Agent 失败不应让整个项目崩溃。** 已完成的模块是资产，不是陪葬品。

### 2.4 Checkpoint（断点）

- **频繁写盘**：每完成一个模块/每次非确定性操作前，更新 `progress.json`
- **崩溃恢复**：重启后读 progress.json，跳过已完成模块，从断点继续
- **恢复信息**：保留"上次进行到哪 + 为什么停"一句话，避免重启后失忆

## 三、上下文管理（防记忆爆炸）

LLM 上下文有硬上限，且 **32K token 以上性能显著衰减**（部分模型从 99% 掉到 70% 以下）。多 Agent 系统的 token 消耗是单 Agent 的 10-15 倍，上下文失控 = 烧钱 + 降智。

### 3.1 主上下文 vs Scratchpad（笔记本）分离

```
主上下文 = 当前对话（只放当下必要信息）
scratchpad = 持久文件（模块清单、文件 map、关键发现、任务进度）
```

- 子 Agent 任务说明必须**自包含**：所有必要信息写进任务文本，不依赖历史上下文
- 大文件放磁盘，让 Agent 按需读取，不塞进上下文
- scratchpad 用简单的 `memory.md`/`progress.json` 即可，不需要复杂基础设施

### 3.2 上下文裁剪公式

上下文超限时按三段处理：
```
保留：最近（完整细节） + 历史（LLM 摘要） + 无关（删除）
```

不要直接删——用一次 LLM 调用把旧上下文压成摘要再保留。

### 3.3 角色指令漂移防护

长会话中 System Prompt 可能被自然淘汰，Agent 角色退化。对策：每 N 轮（如 5 轮）重新注入核心指令。对应到 WorkBuddy：重要约束在每个子 Agent 任务说明里重写一遍，不依赖"之前说过的"。

### 3.4 成本护栏

- 派活前先估预算（档位 × 任务量），异常飙升先怀疑死循环
- 熔断也是成本护栏：连续失败的重试是最烧钱的路径
- 每轮审查结论存档，避免重复审查同一问题
