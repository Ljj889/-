## 三、module_type 显式字段设计（局限 #6 · P0 方案）

> 代码层由**编排 B（平台开发）M_CORE** 实现，本文档层先行固化设计。

**问题**：`_module_kind` 关键词启发式判断模块类型是 LLM 工程头号隐患——"验证"这个词可同时属于"非代码验证"和"集成测试"两种语境（M3 实战案例）。

**设计**：
- `blueprint_decomposed.json` 每个模块对象加显式字段 `"module_type": "code | test | doc | integration"`（架构师拆解时直接写入）；
- 引擎层 `_module_kind` 改为**直接读该字段**，删除所有关键词启发式；
- 执行/审查按 module_type 分派 prompt（code/test 走代码标准；doc 走报告标准；integration 走集成测试标准）；
- 边界测试：用含"验证/检查"字样的 integration 模块用例覆盖分类边界（防回归）。

**验收(EARS)**：当模块含"验证/检查"字样但 module_type=integration 时，系统应走集成测试路径而非报告路径。

## 四、核心洞察

LLM 的缺点不是"不够聪明"——是"它不知道自己什么时候会出错"。所有防线本质上在做同一件事：**给 LLM 装上外骨骼**。

| 缺什么 | 补什么 |
|---|---|
| 缺自我纠错 | 审查段 + 反思段 |
| 缺边界感知 | JSON schema + 重试上限 + 连败即停 |
| 缺外部验证 | 对比外部信息（调研轮询）+ 真跑代码（EXIT=0） |
| 缺注意力管理 | 蓝图粗拆→细拆 + 调研轮询每轮只读 1 篇 |
| 缺决策一致 | 错误路由器（纯规则，不调 LLM）→ references/error_routing.md |

## 五、使用方式

- 设计新 Phase 时：对照本表，看新 Phase 会触发哪些 LLM 局限；
- 写 prompt 时：检查是否防住首尾偏好、上下文污染；
- 出 bug 时：先查本表——是不是已知 LLM 局限的新案例；
- 发现新局限时：加一条到 §一/§二，配实战案例 + 防线 + SKILL.md 落点。
