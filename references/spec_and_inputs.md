## 一、项目材料包（Phase 0 输入）

用户向主 Agent 提交的材料分三类。**蓝图和技术选型是骨架，补充材料是边界和血肉——补充材料缺失是 AI 用"合理默认"跑偏的头号来源，必须显式收集。**

### 三类材料总览

| 类 | 内容 | 作用 | 进流程的哪 |
|---|---|---|---|
| ① 蓝图/框架 | 项目目标、功能范围、整体架构、模块边界 | 骨架 | spec / plan |
| ② 技术选型 | 技术栈、依赖、运行环境、关键库 | 工具 | plan |
| ③ 补充材料 | 业务规则、限制、合规、风格、验收偏好、环境约束 | 边界与血肉 | constitution / lessons / 验收标准 |

### 提交清单模板（用户可直接照着填）

#### ① 蓝图 / 框架

```
- 项目一句话定位：
- 要解决的核心问题：
- 功能范围（做什么 / 明确不做什么）：
- 整体架构（分层 / 模块划分，可用文字或图表）：
- 目标用户/使用场景：
```

#### ② 技术选型

```
- 语言与版本：
- 框架/运行时：
- 关键依赖库（及用途）：
- 运行环境（本机已装什么 / 缺什么）：
- 部署方式（如有）：
```

#### ③ 补充材料（个性化 · 最容易漏 · 最重要）

```
- 业务规则与硬限制（必须遵守、绝对不允许的）：
- 合规要求（行业红线，如广告法、数据安全）：
- 代码风格 / 命名规范 / 目录约定：
- 验收标准偏好（什么算"做完"，尽量用 EARS 语法）：
- 环境约束（如本机没有 ffmpeg、Python 版本限制）：
- 用户习惯 / 使用偏好（如中文报错、要 CLI-first）：
- 已知的坑（上次做类似项目踩过的）：
```

### 材料缺失时的处理规则

1. **能补齐就补齐**：材料包不全时，主 Agent 先列缺失清单问用户，不默认开工。
2. **全权执行模式下**：用户不在场时，缺失项用合理默认 + 在报告里**显式标注假设**（"此处假设 X，实际是 Y 时需调整"）。
3. **运行时补充**：材料不必一次给全——`lessons.md` 就是运行时沉淀的补充材料（环境实测、架构决策、失败教训），每次重开项目先读它。

### 与流程的对应

- ①② 是**事实输入**（项目是什么）→ 进 spec.md / plan.md
- ③ 是**规则输入**（项目怎么约束）→ 进 constitution.md（不可协商）+ lessons.md（环境事实）+ 验收标准（EARS）
- 判断标准："换一个项目还用得上吗"——用得上进技能，用不上留在本项目材料里。

## 二、规格驱动开发（SDD）工作流

SDD 是 2026 年 AI 编码的主流方法论：**先写规格，再让 Agent 实现**。规格是 source of truth，代码是派生品。用它对抗 vibe coding（纯提示词反复试错）的三大问题：歧义变成代码、聊天记录不持久、审查没有靶子。

### 四阶段循环（每阶段有人工门禁）

```
Specify → Plan → Tasks → Implement
 门禁①     门禁②   门禁③      门禁④
spec 未经审查不提交；task 未定义不开始；PR/产物未通过测试不合并
```

1. **Specify**：写规格文档——做什么/为什么做/功能需求/非功能约束（性能、安全）/技术约束/成功标准
2. **Plan**：AI 基于规格生成技术方案——架构决策/技术栈/组件设计/集成点/风险评估
3. **Tasks**：方案拆成可独立测试的小任务——小到可审查、每个含验收标准、可独立实现
4. **Implement**：逐个实现——每次只改合理粒度（一个功能 5-15 个文件、一套可独立跑的测试、一个可审查的提交），每阶段跑 lint/typecheck/test

### 规格四件套（建议放项目根目录）

| 文件 | 内容 | 谁写 |
|---|---|---|
| `spec.md` | 需求 + 非功能约束 + 成功标准 | 人（AI 可起草，人定稿） |
| `plan.md` | 架构 / 技术栈 / 组件 / 集成点 | AI 生成，人审查 |
| `tasks.md` | 可测试任务清单（含验收标准） | AI 生成，人审查 |
| `constitution.md` | 不可协商原则：测试方法、代码约定、安全要求、设计系统规则 | 人 |

**constitution.md 就是"加强版合约"**：合约管单个模块怎么写，constitution 管整个项目怎么定规矩（比如"所有工具函数必须 CLI-first""所有新代码必须带单元测试"）。

### EARS 验收标准语法

模糊的验收标准（"模块工作正常"）是 Agent 自行发挥的根源。用 EARS（Easy Approach to Requirements Syntax）消除模糊：

```
当 <触发条件> 时，系统应 <响应>
WHEN <trigger>, the system SHALL <response>
```

示例：

- 差：`倒计时准确`
- 好：`当用户点击开始且当前状态为"空闲"时，系统应启动 25 分钟倒计时并以秒为单位更新显示`

常用变体：

- 全称：`系统应始终 <行为>`（Ubiquitous）
- 事件：`当 <事件> 时，系统应 <行为>`（Event-driven）
- 状态：`当 <状态> 时，系统应 <行为>`（State-driven）
- 可选：`当 <条件> 时，若 <可选>，系统应 <行为>`（Optional feature）

### 人在回路门禁（谁做最终决策）

AI 可以生成：需求草稿、边界条件、技术方案、测试、实现、Review 建议。
**人必须决定**：业务规则、数据一致性策略、安全边界、架构取舍、是否接受技术债、什么才叫完成。

> 原则：AI 提速打字，人把关方向。spec 是人和 AI 之间的契约，不是 AI 的表演舞台。

### 三个承诺程度

| 程度 | 含义 | 适用 |
|---|---|---|
| spec-first | 规格驱动生成，人仍维护代码 | 大多数项目（推荐） |
| spec-anchored | 规格与代码共同演进 | 规格可能变化的项目 |
| spec-as-source | 规格是唯一可编辑产物，代码完全生成 | 纯生成管线（慎重） |

### 何时不用 SDD

原型/一次性实验/纯视觉快速迭代/小 bug 修复/探索学习——这些用 vibe coding 更快。SDD 是生产系统的纪律，不是所有任务的枷锁。
