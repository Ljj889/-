# 调研学习阶段操作手册（Phase -2）

目的：拆解和写规格之前，用并行调研摸清"别人怎么做"，提炼可复用/可借鉴/可学习的内容，由主 Agent 决策采纳后回流进项目理解。**调研产出的是决策和输入，不是代码。**

## 流程总览

```
读材料 → 定调研方向(2-5个) → 并行派调研Agent → 收报告
→ 逐条采纳决策 → 成果回流(更新架构/规格) → 进入规格先行
```

> **方向讨论 Gate（v3.10.0 · rule 66）**：定调研方向前（D1）与调研采纳后（D2），先向用户提交方向建议卡（建议/理由/备选/风险），确认后再继续——讨论方向，不讨论细节。裁剪规则见 SKILL.md rule 66。

## 〇、调研轮询深度钻探（v3.9 新增 · T7 · LLM 注意力防线）

> 适配：six-layer-orchestrator v3.6+。与 Swarm 并行配合：**Swarm 扫广度，轮询钻深度**。

**为什么**：调研不是"搜一次 → 读 10 篇 → 总结"。LLM 的注意力是有限资源——一次性读 10 篇只能记住表面共通点，吸收不到深层洞察。代码执行可以一次交付，知识吸收必须多轮迭代。

**轮询规则（硬约束）**：
- 每轮**只读 1 篇**（文章/Issue/文档）——多了记不住；
- 每轮**只提取 1-2 个关键洞察**——不是摘要，是"这个信息会改变我们的设计决策吗"；
- 每轮**标注已学**——"前几轮已学到：[摘要]，本轮专注：[方向]"；
- **下一轮关键词基于本轮洞察**——从洞察里长出新的搜索方向，不是凭感觉搜；
- **连续 2 轮无新洞察 → 该方向结束**——是学到没新东西，不是搜到没东西；
- 每条洞察标注级别：`[事实]`（有证据）vs `[假设]`（需验证）。

**执行模板（第 N 轮）**：
```
## 调研轮询 · [主题] · 第 N 轮
### 前几轮已学到
- 第 1 轮：洞察 1 / 洞察 2  |  第 2 轮：洞察 1  |  ...
### 本轮专注
[基于上一轮洞察确定的搜索方向]
### 搜索关键词
[新关键词]
### 阅读材料
[选 1 篇]
### 新洞察
- [事实] 洞察 1：[...]
- [假设] 洞察 2：[...]（或只有 1 个）
### 下一轮方向
[新关键词 + 原因]（连续 2 轮无新洞察 → "该方向调研结束"）
```

**与 Swarm 配合顺序**：先 Swarm 扫一圈（5 方向 × 1 轮 = 5 篇）找到最有价值的方向 → 用轮询深入钻（1 方向 × 3-5 轮）。

**与三种运行模式对应**（rule 55）：高质量 = Swarm 5 方向 + 每方向轮询 5 轮（25 篇）；性价比 = 3 方向 × 3 轮（9 篇）；低成本 = 2 方向 × 2 轮（4 篇）。

## 一、调研方向清单模板

主 Agent 读完蓝图/技术选型/设计细节后，按项目特性定方向（不是固定模板，按项目裁剪）：

```
调研方向：
1. 同类开源项目：搜索与本项目定位最接近的 2-3 个优秀开源项目，分析实现方式
2. 可复用依赖：本技术栈内可直接引用的库/组件（选型理由 + 成熟度）
3. 可借鉴架构：核心难点的架构方案（如：计时引擎的状态机怎么设计、桌宠动画的渲染循环）
4. 可学习最佳实践：本领域特有的坑、规范、设计模式（如：桌面应用 IPC 通信陷阱）
5.（可选）安全/合规/性能基线：本领域的硬性要求
```

判断标准：**每个方向必须回答"对本项目有什么具体价值"**，不做泛泛的知识收集。

## 二、调研 Agent 任务模板（Swarm 并行）

每个方向派一个调研子 Agent，任务说明格式：

```
你是 调研员（角色）
你的目标：围绕【方向 X】搜索优秀开源项目/资料，输出可落地到本项目的具体建议（goal）
执行偏好：只报"对项目有价值"的内容；每条必须写清"是什么 + 为什么对项目有价值 + 怎么落地"；
          不写套话；给出来源链接；区分"可直接复用"与"只能借鉴思想"（backstory）

## 项目背景（主 Agent 注入，控制信息量，只给相关部分）
{项目定位 / 技术栈 / 设计细节片段}

## 输出要求（L3 schema，返回后校验）
{
  "direction": "调研方向名",
  "findings": [
    {
      "title": "项目/资料名",
      "source": "链接",
      "type": "reuse(可直接复用) | idea(可借鉴思想) | framework(可学习框架)",
      "summary": "2-3 句说明它是什么",
      "value": "为什么对本项目有价值（具体到可落地点）",
      "adoption_suggestion": "建议怎么用：直接引入 / 参考实现 / 仅学习"
    }
  ]
}
```

## 三、采纳决策标准

主 Agent 汇总所有报告后，逐条决策：

| 决策 | 条件 | 处理 |
|---|---|---|
| 采纳 | 与项目契合、可落地、有明确收益 | 融入 spec/plan/架构，标注来源 |
| 不采纳 | 与项目冲突、过度设计、维护成本高 | 记录理由，避免以后重复提出 |
| 待定 | 有价值但不明确 | 标记给用户确认，不默认执行 |

**决策原则**：
- 借鉴思想 ≠ 复制代码：开源项目看"为什么这么设计"，不是照搬
- 可复用依赖先查许可证和成熟度，不引僵尸库
- 每次采纳必须能回答"它解决了本项目的哪个具体问题"，答不上来就不采纳

## 四、成果落盘

| 文件 | 内容 |
|---|---|
| `research_report.md` | 所有调研 Agent 的原始报告汇总（含链接） |
| `research_adoptions.md` | 采纳决策清单：采纳了什么、为什么不采纳什么、融入了哪里 |

## 五、回流方式

采纳内容在后续阶段的使用：
1. **架构选型**：plan.md 的技术栈/组件选择引用调研结论
2. **规格**：spec.md 的功能/非功能约束吸收可借鉴的最佳实践
3. **任务拆解**：可复用依赖减少工作量（模块可能缩小或直接引入），可借鉴架构决定模块怎么分
4. **教训预警**：调研发现的"本领域常见的坑"写入 lessons.md 或审查员的检查项

## 成本提醒

调研是真实的多 Agent 开销（搜索 + 阅读 + 汇总），一次调研约等于 2-5 次普通派发成本。控制方法：方向 ≤5 个、每个方向限 1 个调研 Agent、明确要求"只报高价值内容"。
